# C0001 — AI 理解、对话与多角色互动（第一版需求）

- 日期：2026-11-17
- 模块：C / `modules/interaction`
- 状态：已有独立原型与机制测试；真实模型效果与跨模块联调未验收
- 范围：仅聚焦互动模块。当前内部实现采用 Python 标准库；公开接口为模块草案，模型提供方与正式性能阈值后续确定。

## 1. 背景与目标

产品是具有 Meta 感的多角色桌面 AI 陪伴世界。角色能理解用户正在浏览、工作的内容，并与用户及彼此交流，让桌面上的共同经历逐渐形成故事。陪伴是核心，当前不以执行用户工作任务为主要定位，不考虑商业化。

本模块的目标是：让多个角色以各自人设和可见上下文理解同一环境，产生符合情境且彼此有区别的回应；既能主动陪伴，也能接住用户发起的交流，并通过有限、有序、可打断的互动形成共同经历。

角色是否知道自己是 AI、如何理解电脑内外世界、性格和口吻由用户决定，不固定第四面墙台词或世界观。支持多个角色，不把两个角色作为限制。

效果评价关注语境关联、角色差异、消息可见性、自然接话、主动互动克制及失败可恢复。真实模型的表达质量需人工场景评审，不能仅用固定响应测试证明。

## 2. 职责与边界

负责视觉理解、主动观察策略、共享消息 List、按角色筛选上下文、多角色对话调度、文本/视觉模型接入及动作意图选择。

不直接调用操作系统截图，不渲染角色或气泡，不实现身体规则，不生成序列帧，不修改角色创作配置。角色配置和可用动作作为只读输入；真实身体状态及动作结果由 A 模块提供。界面由 D 模块实现，所有连接经装配层注入。

不导入其他业务模块实现、读写其私有状态或要求其他模块同时启动。不提前引入独立故事引擎、长期记忆或关系数据库。

## 3. 功能需求

### 3.1 用户主动互动

- 接收文字、图片、指定角色或全体的交流请求，以及用户主动要求查看桌面的请求。
- 支持单角色交流和群聊，用户可以在角色交流过程中插话。
- 角色主动发言后，用户追问应延续同一上下文；气泡与面板切换不创建另一份对话。
- 图片外的文件类型及具体输入限制待定。

### 3.2 角色主动陪伴

- 接收桌面事件，判断是否需要观察、回应或保持安静。
- 反应可以是文字、动作意图，或两者组合；不是每次观察都必须发言。
- 系统事件与视觉分析使用不同节奏，不把每次窗口变化都转化为模型请求。
- 支持观察范围、暂停和频率控制；通过注入接口请求受控截图。
- 识别画面时刻及来源，处理用户已经切换窗口后的迟到结果，避免把过期内容当成当前画面。
- 避免对自身气泡、角色输出和执行反馈无限自我触发。
- 具体频率、冷却时间、截图保留与排除策略待细化，采集约束由 A 模块实际执行。

### 3.3 多角色交流

- 根据各自人设、可见消息和事件产生不同反应，角色能够接其他角色的话。
- 不要求每个角色对每条输入都回复一次。参与方式可以包含动作或不发言。
- 为自动交流设置明确的结束条件，支持取消、用户插话及有限轮次；具体规则与默认值待确定。
- 单个角色请求失败不应阻塞其他角色和整个会话。
- 对话调度不要求桌面角色聚拢，不依赖角色物理位置决定是否属于群聊。

### 3.4 上下文与消息 List

- 使用同一份有序消息 List，记录发送者、可见/接收范围及顺序，按角色筛选后提供上下文。
- 指定角色的交流不自动暴露给其他角色；公共消息可供参与者使用。
- 本模块是消息和可见性规则的唯一权威来源，向界面提供获准展示的视图。
- 群聊、私聊及角色间公开交流需要区分范围，但不为每只角色建设独立存储系统。
- 长期保存、摘要、截断、跨会话恢复和复杂关系系统暂缓，不承诺重启后自动延续故事。

### 3.5 故事和关系

- 通过事件、角色反应、互相回应和后续提及形成故事，允许表达友情、亲情等关系。
- 用户既能作为角色聊天、分享、调解，也能作为导演注入突发事件或设置故事起点。
- 角色依据人设和当前可见上下文反应，用户不必预写结局。
- 当前通过 List 保留本次上下文中的经历，不以虚构未发生历史来弥补缺失记忆。
- 轻度参考《Tomodachi Life: Living the Dream》的生活趣事与适度干预，不照搬小镇经营、经济、建筑或复杂剧情系统。
- 新闻回顾、离线故事推进、章节和任务系统均不是本版确定需求。导演事件是否让角色知道由用户安排、编辑形式及初始关系配置方式待定。

### 3.6 动作意图与模型调用

- 从角色已有动作描述中选择符合情境的动作意图，不凭空假定新动画已经存在。
- A 模块负责身体状态校验和实际执行，本模块消费接受、拒绝、完成等反馈，不把请求发出等同于动作完成。
- 文本与视觉模型接入封装在本模块内部，允许替换提供方及使用固定响应替身。
- 请求支持取消、超时、错误与过期结果处理；不让模型等待影响即时身体响应。
- 密钥通过外部配置注入，不写入角色包或日志。调试记录应能关联输入事件、目标角色、模型任务和动作结果。

## 4. 输入输出与状态归属

| 类别 | 内容 |
| --- | --- |
| 输入 | 角色配置快照、动作说明、用户消息和图片、桌面事件、观察结果、故事事件、动作执行反馈 |
| 输出 | 有序消息视图、动作意图、观察请求、会话与处理状态 |
| 唯一拥有 | 消息 List、可见性筛选、轮次、主动互动策略、模型任务生命周期 |
| 注入依赖 | 文本/视觉提供方、截图接口、时钟、事件输入与输出接口 |

请求和结果需可关联，附带必要的来源、时间和角色标识；正式字段与协议版本待定义，不暴露框架对象或平台句柄。公共契约修改需与相关模块同步样例及兼容说明，不要求消费者读取本模块内部状态。

## 5. 独立运行与验收要求

提供命令行或最小测试入口，使用三个或更多角色样例、假模型、固定图片/截图和可控时钟，独立观察消息和动作输出，不依赖真实桌面、其他模块进程或模型密钥。三个只是覆盖多角色的样例数量，不是产品上限。

| 场景 | 预期可观察结果 |
| --- | --- |
| 用户对全体分享图片 | 各角色收到正确上下文，能够输出差异化响应与动作意图 |
| 用户只向指定角色发消息 | 其他角色输入上下文中不出现该私聊内容 |
| 角色主动评论后用户追问 | 同一 List 延续交流，无需新建会话 |
| 自动角色对话 | 达到设定条件停止；用户可插话或取消，不无限自聊 |
| 暂停观察 | 停止新的主动采集与分析，已在途结果按明确规则处理 |
| 截图结果迟到或角色移除 | 不误关联新场景，不继续对已移除角色发布结果 |
| 单个模型超时或失败 | 输出失败状态，其他角色和会话继续可用 |
| 动作被拒绝 | 不记录为已完成，不编造成功结果 |
| 用户注入故事事件 | 形成可追踪的事件与角色交流，后续基于 List 正确提及 |
| 退出与取消 | 请求、订阅及后台任务能够释放 |

自动测试验证数据隔离、顺序和调度规则；真实模型场景评审另外检查角色差异、陪伴感与自然交流。独立原型的启动命令与操作步骤见 [运行与验收](../interaction/运行与验收.md)，执行证据及未验证范围见 [验证记录](../interaction/验证记录.md)，不能把机制测试当作真实表达效果验收。
